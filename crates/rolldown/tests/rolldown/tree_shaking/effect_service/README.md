# Effect service shaking fixtures

Real-`effect` programs for `experimental.effectServiceShaking` (EFF-3430). Each fixture is bundled by the integration harness with the option on, then `_test.mjs` imports the bundle (the program asserts its own behaviour) and checks which names stayed in `dist/main.js`. There are no snapshots: the bundles contain the `effect` package and would be noise. Every program also runs unbundled with `node main.js` from its directory, except `external_unresolvable`, `external_effect_run`, `opaque_runtime_objects` and `opaque_wrapped_service`, whose external module is written by `_test.mjs` after bundling.

Run them with:

```sh
cargo test --profile effect-verify -p rolldown --test integration -- tree_shaking__effect_service
```

0 red, 253 green.

### Memory cap

The analysis runs inside the test process, so a solve that never terminates would keep allocating until the host runs out of memory. A runaway like that hit 45 GiB in 75 seconds. Every fixture with `effectServiceShaking` on, and every acceptance program, runs under `rolldown_testing::memory_guard`. When the test process's resident memory goes over `ROLLDOWN_TEST_MAX_RSS_MB` (default 6144), the guard prints the guarded tests that are still running and exits the process. `0` turns the guard off. Measured peaks with the pass absent are about 650 MiB for this suite and 370 MiB for the acceptance set, counting the Node child processes. The cap applies to the whole process, so it is sized for runs filtered to these tests. To bound a run from outside as well, wrap it: `systemd-run --user --scope -p MemoryMax=8G -p MemorySwapMax=0 cargo test ...`.

### Budget and time limit

Each fixture's analysis runs with an entries budget of 100k (points-to and copy entries), set by the harness (`rolldown_testing::effect_fixture`) unless the fixture's config sets `effectServiceShakingMaxEntries`. The largest fixture solve takes about 17k. Three fixtures set their own budget to check that a stopped analysis keeps every method: `budget_exceeded_keeps_every_method` (1000), `module_hole_budget_terminal` (5000, the first of two solves goes over) and `deferred_generation_budget` (9000, the solve goes over while generating a deferred statement). Each fixture must also finish within 2 s, every build and its `_test.mjs` included. The harness runs each fixture in a child process and stops what the fixture starts, at the deadline (so a hung analysis or test script fails in 2 s) and when the fixture finishes. Where the fixture's processes are contained (a PID namespace on Linux, a job object on Windows) it stops the whole process tree. Elsewhere (macOS, and Linux hosts without unprivileged user namespaces) it stops the process group and warns that a process which left the group (`detached: true`) may still be running; Tim accepted that on 2026-11-10, since no fixture starts a detached child. The macOS and Windows paths are compiled and linted but have not been run on those hosts. See `rolldown_testing::effect_fixture`. `ROLLDOWN_TEST_EFFECT_FIXTURE_TIME_LIMIT_MS` changes the limit, and `0` disables it, running the fixture in the test's own process. The slowest fixture usually takes 0.7 to 0.9 s in a parallel run on a 16-core host.
