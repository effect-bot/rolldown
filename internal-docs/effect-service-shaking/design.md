# Effect service shaking — Design & Principles

## Summary

`experimental.effectServiceShaking` (EFF-3430) removes methods of Effect service implementations that nothing left in the bundle can read. An application provides a service (`Layer.succeed(FileSystem, impl)`, a generated API client with hundreds of operations) and uses a few of its methods. Rolldown's tree shaking keeps the whole implementation object, and through it every schema and helper the unused methods reference. The pass proves which methods can never be read, deletes them from the object literals, and lets ordinary tree shaking drop what only they used. The contract with users is that **behaviour never changes**. A method is removed only when no code still in the bundle can read it. Whenever the pass cannot prove that, it keeps the method. For the machinery, see [implementation.md](./implementation.md).

## Design principles / Goals

1. **Soundness over size.** If the analysis cannot tell whether code still in the bundle reads a method, the method stays. Anything the pass does not understand keeps methods: an unresolvable computed name, enumeration, or a service handed to code it cannot see (externals, builtins, `eval`, non-static loaders). A service bails when unseen code can reach it through ordinary values it was given, now or later: the service itself, or a plain object, array or other ordinary value that holds it. Effect's containers are not a path: an Effect, Context, Layer, ManagedRuntime, MemoMap or Fiber handed over bails nothing, and neither does a service reached only through one of them, a key, or an Effect primitive. When `o.m()` calls unseen code, only the receivers whose own `m` slot can hold that code (or that have no own `m`) are handed over, so an external value among a service's possible values does not leak the bundled implementation. The cost of not understanding something is bounded **per key**, not per build. An unknown name read on the value of key `K` keeps every method of `K` and nothing else. A key whose string is unknown aliases every key.
2. **One generic analysis, one small Effect model.** The analysis is an inclusion-based (Andersen) points-to analysis over every bundled module: flow-insensitive, field-sensitive on constant names, with on-the-fly reachability. A function body is analysed only once something may call it, so the reads inside a method nothing reads never count. The same holds for top-level statements that Rolldown finds free of side effects: such a statement is analysed once reachable code references a symbol it declares, reads that export through a module namespace, or uses the namespace wholesale. Statements with side effects, imports and re-exports, and entry modules run eagerly. Effect knowledge sits only in rules bound to the canonical symbols of `@stability stable` exports of the public `effect` modules (`Context`, `Layer`, `Effect`, `Fiber`, `Scope`, `ManagedRuntime`, `Function`, `Pipeable`, `Tracer`), plus a few listed exports of modules that are otherwise ordinary code (`Formatter.format`, `Formatter.formatJson`, `Equal.equals`, `Hash.hash`; principle 9). There are no trusted packages, no path prefixes and no annotations: everything else, including the rest of `effect` (Schema, HttpRouter, FileSystem, …), is ordinary code. An export of a modelled module without an explicit rule gets the default rule. The default is sound by construction: callbacks receive every argument-derived value at every parameter position, and the result yields the same. It never hands out a Fiber or a Context. Those reach bundled code only through stable APIs that hand one out (`Effect.withFiber`, `Effect.context`, `Fiber.getCurrent`, …), each with its own rule, and the issue's first assumption is that code the pass does not look inside reaches no service through a Fiber or any other Effect container. Binding precedence does not depend on walk order: an explicit rule beats a declared Key, which beats the default.
3. **Context sensitivity only where Effect needs it.** Effect is built on a few higher-order helpers (`dual`, `pipe`, `flow`, the `pipe` method). These are modelled directly, including a bundled `pipe() { return pipeArguments(this, arguments) }`, which is the `Pipeable.pipe` method, because otherwise one summary would merge every call site in the program. Small leaf higher-order functions are cloned per call site, with bounded depth and clone count. Everything else shares one summary.
4. **Never prune what the runtime reads by itself.** `Context.Reference` keys (keys with a default value), `Scope`, `Layer.CurrentMemoMap`, `Tracer.ParentSpan` and `effect/Metric/FiberRuntimeMetrics` are read by the fiber runtime by key string. Their providers are never edited.
5. **Methods only.** Only properties whose value the analysis proves is always a function are eligible. Formatters observe data properties and getters (`JSON.stringify`, `util.inspect`) but not method bodies, so data properties, getters, setters and `__proto__` stay. An initialiser that can be observed also stays: one that is impure or could throw (TDZ reads, imported bindings).
6. **Bounded cost.** The pass has an allocation budget (objects, variables, points-to entries). Going over it bails the whole analysis: every method is kept and the build is unchanged. This prevents a runaway solve from exhausting the host. The time target is at most 1.5× the build without the pass until a dedicated performance phase, then 1.2× or less.
7. **Switching itself off is visible.** The pass does no work in two cases, and both emit one `EFFECT_SERVICE_SHAKING` warning. The first is that `effect` is external, so no primitive can be recognised. The second is a model mismatch: an unsupported major version, or a ruled export missing from the installed `effect`. A bundle without `effect` is silently left alone.

### Rejected alternatives

- **A syntactic pass over recognised call shapes** (the first prototype). Fast, but it trusts the shapes it recognises. Real providers are built through named callbacks, `Effect.all` and pipeables, so it was either unsound or bailed globally.
- **Trusted-module allowlists** (treat `effect/*` internals as clean without analysing them). This is unsound against Effect code that enumerates a Context (formatters, `Equal`, custom loggers), and it ties the pass to internal file layout. The pass analyses those modules instead.
- **Analysing `effect`'s internal modules generically instead of the default rule.** We tried it: it merges more values, not fewer. Re-measured in two forms:
  - **Whole modules.** Every acceptance program goes over the entries budget, `node_file_system` included: 227k variables and 13M points-to entries, against 87k variables within budget.
  - **Closed exports only.** This form covers the internal exports that no rule or key claims and that read nothing but imports, the module's own exports and globals (175 declarations). `node_file_system` stays within the budget, but its solver steps rise from 183k to 2.4M. `effect_internal_analysed`, `distilled_stripe` and OpenAI all go over.

  In both forms the values merge through the structural helpers that the runtime's shared prototypes call on `this` (`Equal`, `Hash`, `Inspectable`, `Formatter`, `Chunk`). Each helper has one summary, and that summary ends up holding most of the program's objects. So the internal modules behind the ruled exports stay behind rules.

8. **Public types bound bundled code** (the issue's second assumption). User and third-party code uses Effect's objects only in ways that type check against Effect's public types. So the model gives each object only its public members: an Exit (from `Effect.exit`, `Fiber.await`, `fiber.addObserver`, `pollUnsafe`, `onExit`, `run*Exit`, `acquireUseRelease`'s release) has `_tag`, `value` and `cause`; any other Effect has none of them, and a read of a member the types don't have records nothing. The assumption does not cover `effect`'s own code, which is analysed generically; reflection on a Context or Runtime there still bails. The types also bound value flow (Tim's decision): a value whose kind a public parameter or return type of `effect` cannot hold never reaches or leaves that function. The pass reads the `.d.ts` next to each bundled module of the installed `effect`, with no type checker, when an exported function is first called. Each parameter and return gets the kinds it admits: primitives, functions, arrays, records of primitives, objects with given members, or anything. A bounded edge passes only admitted objects; an object a later field, prototype, accessor, unknown store, spread or escape could make admissible is re-checked when that happens. A summary (a default-rule wrap or an opaque value) at a primitive-only position becomes an unknown scalar rather than being dropped. A position declared exactly `unknown` or `any` in a public module (a parameter, a rest parameter's elements, a record or index signature of them) is ignored (Tim's decision): it admits only primitives, a summary there becomes a plain primitive, and what reaches it goes to one program-wide protocol walk (principle 9) instead. A return at such a type gives the caller a primitive, even after narrowing. Tim's span decision adds the public `Tracer` types `Span`, `AnySpan`, `ExternalSpan`, `NativeSpan` and `SpanLink` as ignored types. The function an export returns directly (`return (input) => …`, as in `Schema.decodeUnknownSync(schema)(input)`) is bounded by the declared return type's call signatures. A default-modelled export (principle 3) takes its `.d.ts` bounds too: an argument at an ignored position is walked and nothing else of it is read, and a callback passed directly receives, at each position its declared parameter type bounds, only the argument-derived values that type admits (`useSpan`'s `span: Span` receives none). Type parameters (never their constraints, so `dual` stays open), `object`, mapped and indexed types, `unknown`/`any` in `internal/` modules, and anything the resolver cannot follow are open, so a gap in the resolver never drops a flow. The same check applies where a model rule runs a plain object as an Effect (`Effect.map(obj, f)` and the like): Effect's type requires the `~effect/Effect` member, so an object that can't have it is not run, and waits like any rejected value.
9. **Effect's own formatting and structural equality keep nothing** (Tim's decisions). What reaches an ignored position (principle 8: `Formatter.format`'s and `Inspectable`'s input, log messages and annotations, span attributes, `Predicate` checks), and structural `Equal.equals` and `Hash.hash`, are modelled as walks. Formatting has no rule of its own any more: `Formatter.format(input: unknown)` is bounded like any public function. A walk reads none of a value's keys, so it demands nothing and bails nothing. Everything the value holds, now or later, is walked in turn. The walk calls the protocol methods the real code calls on each object it reaches, the way `obj.toString()` in bundled code would: those methods are read, and their bodies run. The protocol walk calls the methods the issue's protocol exception lists (`toJSON`, `toString`, `valueOf`, `[Symbol.toPrimitive]`, the inspect symbol, `[Equal.symbol]`, `[Hash.symbol]`, `[Redactable.symbolRedactable]`, `[HttpServerRespondable.symbol]`) and a Date's `toISOString`. `[Redactable.symbolRedactable]` receives the current Context and `[util.inspect.custom]` Node's arguments (with the `util.inspect` builtin as its inspector); every other argument is a primitive. `Tracer.make` returns the tracer it is given. A walked value with a callable `then` is a hand-written thenable and bails, as an adopted one does: adopting an object that is not a native Promise and has a callable `then` (an `await`, an async return, a promise resolution) escapes it to code the pass can't see, so every service it reaches keeps every method, and the await yields an unknown value; native Promises are followed exactly. Hashing calls `[Hash.symbol]`, and a Date's `getTime`/`toISOString` or a RegExp's `toString`. Equality hashes both sides and calls `[Equal.symbol]` with the compared values that have one, since `compareStructure` calls it only when both sides do. Equality walks each call site separately, so that one site's values don't reach another site's `[Equal.symbol]` (`Data`'s enumerates its argument). The protocol walk and hashing each have one walk for the whole program. A comparison, hash or printed output may change when an unread method is removed, and that is accepted. Plain JavaScript enumeration in user or third-party code still bails, and so do Context construction and lookups by key. Host formatting (`String(x)`, `JSON.stringify`, `console.*`, `util.inspect`) runs the protocol methods it calls the same way.
10. **Services never enter the error channel** (the issue's third assumption). No service, and no value holding one, is a typed failure, a defect or anything a Cause carries, including values thrown inside Effect code. So the pass does not track the error channel: an Effect's failures, `Exit.cause` and Cause's functions yield nothing, and a read through them keeps nothing and bails nothing. Handlers (`catch*`, failure branches, `Cause.map` callbacks) still run, so the services they capture count. Plain JavaScript `throw`/`catch` outside Effect is analysed as ordinary code. The one exception is the `Done` signal (`Cause.done`) a Schedule or Pull ends with: it carries a final output, success-side data, so handlers see a program-wide `Done` holding every such output. Services never pass through a Schedule either (the issue's fourth assumption): `Effect.repeat`, `retry` and `retryOrElse` step a Schedule's own code with its input minus what is definitely a service (an object whose allocation provably runs once and which is the only value some provider holds: module top-level code outside loops and class bodies; ordinary objects, and objects from sites that may run more than once, keep their structure, so a field may still name a method) and return only the primitives of the `Done` value it ends with (each step's decision reaches only `Schedule.CurrentMetadata`'s `output`), so neither their result, `orElse`'s output argument nor `Schedule.CurrentMetadata` carries a service. The callbacks a Schedule is built from still run. Removing the `Done` exception, the assumption's other half, waits on Tim's decision about Channels and Sinks. The pool stays program-wide (Tim declined a per-site `Done` flow): every `Cause.done` value joins one pool, so a Schedule's final output read back through `Effect.repeat` or `retryOrElse`'s fallback also holds other Schedules' `Done` values, including primitives such as `recurs`' attempt counter. When such an output is used as a computed method name, the read is an unknown key and the service keeps every method. This is accepted imprecision: it is sound and rare, and the `Done` pool was on no OpenAI or Stripe witness path. Revisit trigger: if a gate measurement ever shows the `Done` pool on a witness path, a per-site `Done` flow goes back to Tim with that evidence.

11. **`effect`'s library modules are modelled from their `.d.ts`, not their bodies** (Tim's decision; opt-in for now with `ROLLDOWN_EFFECT_SERVICE_SHAKING_TYPEMODEL=1`). Every module of the `effect` package that is not a primitive (the modules `MODULES` names and those their ruled exports resolve into) is type-modelled: its body and module-level code are not analysed, and each export is a summary (`ObjKind::Typed`). Listed modules keep their listed rules. A call into one follows the declared signature, with one slot per call site standing for every type parameter:
    - each argument, filtered by its declared type (`unknown`/`any` ignored and walked for protocols, primitive-only types passing primitives), contributes to the slot: a plain value joins it; a summary's contents flow in, and the call's arguments flow back into that summary (a container's setter); an Effect contributes its success; an array its elements;
    - callbacks, passed directly or held in an options object (whose members all count as read), run with the slot, and their results join it; so does a function a summary holds;
    - a key handed over keeps every method; a key declared inside a type-modelled module keeps every method too (that code uses its service invisibly), which is why a service built by `effect` code (`HttpClient.make`, `FileSystem.make`) is not pruned;
    - the result follows the declared return: an `Effect` (succeeding with a summary, and with the slot when its success is a type parameter), the slot for a bare type parameter, a primitive, or a summary holding the slot; without a signature, both.

    Members read off a summary give its slot (and the summary itself, as a method). Slots never hold summaries themselves: one held there contributes its contents and is stood for by one shared summary, and method calls at one site share one result whatever the receiver; both bound otherwise quadratic or unbounded growth. Status: the Schema fixtures that stopped at the budget now complete, but OpenAI and Stripe still stop (the budget fills with the generated clients' own Schema records and call results), NodeFileSystem completes without pruning (its service is `effect/FileSystem`'s `make`), and several fixtures lose precision (no miscompile observed in the ones run).

## Unresolved Questions

- **Precision on Schema-heavy programs.** The `effect_internal_analysed` fixture, the OpenAI generated client and the Distilled Stripe programs still keep every method. Schema's AST classes are recursive and their methods (`_rebuild`, `recur`, `flip`) are called from about 900 sites each. Per-call-site cloning reaches its cap, so the values merge. Until `0bf641510` the `effect:default` rule also handed its callbacks a phantom Fiber, which carried the ambient Context into Schema code (SchemaAST's `parseUnion`, an `iterateEager` callback, through `resolveConcurrency` and friends from `internal/effect.js`). Reading Schema fields on it counted as reflection on a Context, so every key bailed early.

  The default no longer invents that Fiber, and explicit rules bind before the default (`internal/effect.js`'s own `map`, `flatMap`, … take their stable rules). Removing the phantom Fiber removed the early bail, but not the merging underneath: the Schema solves now run until they exceed the entries budget instead. `schema_concurrency_no_fiber` goes over 16M entries, and over 60M too when the limit is raised as a diagnostic (336k variables, 144M steps, 236 s). `effect_internal_analysed` and `distilled_stripe`, which stayed within the budget only because of the early bail, now go over it. No program removes fewer methods than before, since all three removed none. Stepping Schedules through generic `Schedule`/`Duration` code (the `Effect.repeat` rule) shows the same merging: in `internal_combinator_caller` the ambient Context reaches `Duration` reads (`millis`, `nanos`).

- **Effect's containers** are settled by principle 8 and Tim's container decisions: a named read on a Context, Layer, ManagedRuntime or MemoMap is a public member with a rule or reads nothing; writes, unknown-name reads, enumeration and spread bail nothing; `mapUnsafe`, MemoMap (all of it, including `ManagedRuntime.memoMap`) and Context equality and hashing are ignored and keep nothing; a Context handed to an API without a model yields its services; `Context.get(ctx, key)` reads a key's services only when `ctx` may be a Context; a write to `ManagedRuntime.cachedContext` provides its Context.

- **Sealing model objects** is settled by principle 8: an unruled member of a model object reads nothing, which is sound under the public-types assumption, so no seal is needed.

- **What blocks the OpenAI and Stripe gates.** Traced on OpenAI at the escape/public-types increment (the per-variable census used a temporary instrumentation patch, not committed):
  - Before: 13.5M points-to entries plus 2.6M copies, over the 16M budget. 8.3M of the entries were fields of about 555 `.annotate({...})` literals from the generated client, each holding about 544 values. They came from `Effect.exit` inside `SchemaAST`'s struct parser: its result was a Wrap, and the wraps of six such calls each held about 645 objects as both wrapped values and callbacks, so every closure reaching them (`InternalRecord.assignProperty` among them) ran with every value in every parameter.
  - After `Effect.exit` produces an Exit: field entries drop to 0.37M. The total stays at 13.9M plus 2.1M copies, still over, and the solve does not fit in 60M entries either (diagnostic only). The rest is merging in Schema construction: `internal/schema/make.js`'s `make(ast)` allocates its `function Schema() {}` once for every schema in the program, so about 10k objects (the generated client's field and annotation literals and the ASTs built from them) flow through one shared set of `SchemaAST` helpers. Each of those helpers is cloned up to the 64-clone cap and every clone holds the whole set. About 3,600 variables hold more than 2,000 objects each.
  - Stripe hits the same budget the same way (10.7M entries plus 5.3M copies).
  - Most of those schemas are dead: the generated client builds them at module top level, and only the schemas of the methods the program calls are ever used. Lazy activation of top-level statements (principle 2) now keeps them out of the solve until referenced.
  - With lazy activation, OpenAI and Stripe still go over the budget (OpenAI 15.0M points-to entries plus 1.0M copies, Stripe 15.1M plus 1.6M). An earlier prototype looked better because import statements were lazy too: each overwrote the real declaration it imports, so references activated an empty import statement and live code was skipped (`lazy_toplevel_activation` catches this). In that prototype's census the remaining mass sat in the request-building helpers of `effect/http` (`Headers.set`, `HttpClientRequest.setHeader`/`setUrl`, `UrlParams.fromInput`), whose `self` parameters held about 840 objects, mostly site-less model objects, with each helper cloned up to the 64-clone cap. That needs re-tracing against the landed version.
  - Re-traced at `4cc0655ec`: the first unwanted merge on both programs was the `dual` model. `dual.fn` read the dual's arity through a load that had not propagated when the rule fired, so it took both branches and every full call also returned a partial. The partials then flowed as data into request `headers` and `urlParams` everywhere. `Function.dual` now records a literal arity on the builtin. With that fixed, both programs are still over the budget; the next merge is in the shared `pipe()` methods of `HttpClient` and `HttpClientRequest`, whose per-clone `arguments` arrays end up together with the generated client's request arrows.
  - Contexts are not the next lever until that merge is understood.

- **Performance.** On the OpenAI acceptance program the build takes about 6 s with the pass and 270 ms without, and Stripe about 33 s against 63 ms (both over budget, so the time measures where the solve stops). That is far over the 1.5× target. Possible fixes: caching `effect`'s constraint graph across builds, SCC collapsing, and tracking only values that can reach a key.
- **Order sensitivity.** The same input gives the same solve: modules and exports are walked in a canonical order (implementation.md, Data flow step 2). The solve is not order-independent, though. Clones and builtin rule invocations go to the first call sites to arrive, so an unrelated change that reorders execution can change precision and the budget verdict. Walking `effect_internal_analysed` in reverse execution order gives about 340k variables and goes over the budget; execution order gives 310k and stays within it. Making the caps independent of arrival order (choosing clone sites by rank, not by arrival) would remove this. It is open whether that is worth its cost.
- **Entry exports.** The exports of user entry modules are still handed to unseen code (`mod.rs`). With application builds only, nothing outside the bundle consumes them, so this can go.
- **Later increments.** Prefix narrowing of keys built from a constant prefix plus a run-time suffix (the `dynamic_key_prefix` fixture is red until then), and pruning class-instance services' prototype methods.
