# Effect service shaking — Design & Principles

## Summary

`experimental.effectServiceShaking` (EFF-3430) removes methods of Effect service implementations that nothing left in the bundle can read. An application provides a service (`Layer.succeed(FileSystem, impl)`, a generated API client with hundreds of operations) and uses a few of its methods. Rolldown's tree shaking keeps the whole implementation object, and through it every schema and helper the unused methods reference. The pass proves which methods can never be read, deletes them from the object literals, and lets ordinary tree shaking drop what only they used. The contract with users is that **behaviour never changes**. A method is removed only when no code still in the bundle can read it. Whenever the pass cannot prove that, it keeps the method. For the machinery, see [implementation.md](./implementation.md).

## Design principles / Goals

1. **Soundness over size.** If the analysis cannot tell whether code still in the bundle reads a method, the method stays. Anything the pass does not understand keeps methods: an unresolvable computed name, enumeration, or a service handed to code it cannot see (externals, builtins, `eval`, non-static loaders). A service bails when unseen code can reach it through ordinary values it was given, now or later: the service itself, or a plain object, array or other ordinary value that holds it. Effect's containers are not a path: an Effect, Context, Layer, ManagedRuntime, MemoMap or Fiber handed over bails nothing, and neither does a service reached only through one of them, a key, or an Effect primitive. When `o.m()` calls unseen code, only the receivers whose own `m` slot can hold that code (or that have no own `m`) are handed over, so an external value among a service's possible values does not leak the bundled implementation. The cost of not understanding something is bounded **per key**, not per build. An unknown name read on the value of key `K` keeps every method of `K` and nothing else. A key whose string is unknown aliases every key.
2. **One generic analysis, one small Effect model.** The analysis is an inclusion-based (Andersen) points-to analysis over every bundled module: flow-insensitive, field-sensitive on constant names, with on-the-fly reachability. A function body is analysed only once something may call it, so the reads inside a method nothing reads never count. Effect knowledge sits only in rules bound to the canonical symbols of `@stability stable` exports of the public `effect` modules (`Context`, `Layer`, `Effect`, `Fiber`, `Scope`, `ManagedRuntime`, `Function`, `Pipeable`, `Tracer`). There are no trusted packages, no path prefixes and no annotations: everything else, including the rest of `effect` (Schema, HttpRouter, FileSystem, …), is ordinary code. An export of a modelled module without an explicit rule gets the default rule. The default is sound by construction: callbacks receive every argument-derived value at every parameter position, and the result yields the same. It never hands out a Fiber or a Context. Those reach bundled code only through stable APIs that hand one out (`Effect.withFiber`, `Effect.context`, `Fiber.getCurrent`, …), each with its own rule, and the issue's first assumption is that code the pass does not look inside reaches no service through a Fiber or any other Effect container. Binding precedence does not depend on walk order: an explicit rule beats a declared Key, which beats the default.
3. **Context sensitivity only where Effect needs it.** Effect is built on a few higher-order helpers (`dual`, `pipe`, `flow`, the `pipe` method). These are modelled directly, because otherwise one summary would merge every call site in the program. Small leaf higher-order functions are cloned per call site, with bounded depth and clone count. Everything else shares one summary.
4. **Never prune what the runtime reads by itself.** `Context.Reference` keys (keys with a default value), `Scope`, `Layer.CurrentMemoMap`, `Tracer.ParentSpan` and `effect/Metric/FiberRuntimeMetrics` are read by the fiber runtime by key string. Their providers are never edited.
5. **Methods only.** Only properties whose value the analysis proves is always a function are eligible. Formatters observe data properties and getters (`JSON.stringify`, `util.inspect`) but not method bodies, so data properties, getters, setters and `__proto__` stay. An initialiser that can be observed also stays: one that is impure or could throw (TDZ reads, imported bindings).
6. **Bounded cost.** The pass has an allocation budget (objects, variables, points-to entries). Going over it bails the whole analysis: every method is kept and the build is unchanged. This prevents a runaway solve from exhausting the host. The time target is at most 1.5× the build without the pass until a dedicated performance phase, then 1.2× or less.
7. **Switching itself off is visible.** The pass does no work in two cases, and both emit one `EFFECT_SERVICE_SHAKING` warning. The first is that `effect` is external, so no primitive can be recognised. The second is a model mismatch: an unsupported major version, or a ruled export missing from the installed `effect`. A bundle without `effect` is silently left alone.

### Rejected alternatives

- **A syntactic pass over recognised call shapes** (the first prototype). Fast, but it trusts the shapes it recognises. Real providers are built through named callbacks, `Effect.all` and pipeables, so it was either unsound or bailed globally.
- **Trusted-module allowlists** (treat `effect/*` internals as clean without analysing them). This is unsound against Effect code that enumerates a Context (formatters, `Equal`, custom loggers), and it ties the pass to internal file layout. The pass analyses those modules instead.
- **Analysing `effect`'s internal modules generically instead of the default rule.** We tried it: it merges more values, not fewer. Re-measured in two forms:
  - **Whole modules.** Every acceptance program goes over the entries budget, `node_file_system` included: 227k variables and 13M points-to entries, against 87k variables within budget.
  - **Closed exports only.** This form covers the internal exports that no rule or key claims and that read nothing but imports, the module's own exports and globals (175 declarations). `node_file_system` stays within the budget, but its solver steps rise from 183k to 2.4M. `effect_internal_analysed`, `distilled_stripe` and OpenAI all go over.

  In both forms the values merge through the structural helpers that the runtime's shared prototypes call on `this` (`Equal`, `Hash`, `Inspectable`, `Formatter`, `Chunk`). Each helper has one summary, and that summary ends up holding most of the program's objects. So the internal modules behind the ruled exports stay behind rules.

8. **Public types bound bundled code** (the issue's second assumption). User and third-party code uses Effect's objects only in ways that type check against Effect's public types. So the model gives each object only its public members: an Exit (from `Effect.exit`, `Fiber.await`, `fiber.addObserver`, `pollUnsafe`, `onExit`, `run*Exit`, `acquireUseRelease`'s release) has `_tag`, `value` and `cause`; any other Effect has none of them, and a read of a member the types don't have records nothing. The assumption does not cover `effect`'s own code, which is analysed generically; reflection on a Context or Runtime there still bails.

## Unresolved Questions

- **Precision on Schema-heavy programs.** The `effect_internal_analysed` fixture, the OpenAI generated client and the Distilled Stripe programs still keep every method. Schema's AST classes are recursive and their methods (`_rebuild`, `recur`, `flip`) are called from about 900 sites each. Per-call-site cloning reaches its cap, so the values merge. Until `0bf641510` the `effect:default` rule also handed its callbacks a phantom Fiber, which carried the ambient Context into Schema code (SchemaAST's `parseUnion`, an `iterateEager` callback, through `resolveConcurrency` and friends from `internal/effect.js`). Reading Schema fields on it counted as reflection on a Context, so every key bailed early.

  The default no longer invents that Fiber, and explicit rules bind before the default (`internal/effect.js`'s own `map`, `flatMap`, … take their stable rules). Removing the phantom Fiber removed the early bail, but not the merging underneath: the Schema solves now run until they exceed the entries budget instead. `schema_concurrency_no_fiber` goes over 16M entries, and over 60M too when the limit is raised as a diagnostic (336k variables, 144M steps, 236 s). `effect_internal_analysed` and `distilled_stripe`, which stayed within the budget only because of the early bail, now go over it. No program removes fewer methods than before, since all three removed none. Stepping Schedules through generic `Schedule`/`Duration` code (the `Effect.repeat` rule) shows the same merging: in `internal_combinator_caller` the ambient Context reaches `Duration` reads (`millis`, `nanos`).

On the larger programs the solve can also go over its allocation budget. OpenAI does, on points-to entries. Candidate directions:

- a typed filter on the default rule's results and callback arguments;
- object-sensitivity for method calls on class instances, which the structural helpers above would also need before the internal modules could be analysed generically;
- not treating reads of names a Context cannot have as reflection.

Each must be argued against principle 1. The precision problem is now plainly the merging in generic code, not the model's rules.

- **Sealing model objects** is settled by principle 8: an unruled member of a model object reads nothing, which is sound under the public-types assumption, so no seal is needed.

- **What blocks the OpenAI and Stripe gates.** Traced on OpenAI at the escape/public-types increment (the per-variable census used a temporary instrumentation patch, not committed):
  - Before: 13.5M points-to entries plus 2.6M copies, over the 16M budget. 8.3M of the entries were fields of about 555 `.annotate({...})` literals from the generated client, each holding about 544 values. They came from `Effect.exit` inside `SchemaAST`'s struct parser: its result was a Wrap, and the wraps of six such calls each held about 645 objects as both wrapped values and callbacks, so every closure reaching them (`InternalRecord.assignProperty` among them) ran with every value in every parameter.
  - After `Effect.exit` produces an Exit: field entries drop to 0.37M. The total stays at 13.9M plus 2.1M copies, still over, and the solve does not fit in 60M entries either (diagnostic only). The rest is merging in Schema construction: `internal/schema/make.js`'s `make(ast)` allocates its `function Schema() {}` once for every schema in the program, so about 10k objects (the generated client's field and annotation literals and the ASTs built from them) flow through one shared set of `SchemaAST` helpers. Each of those helpers is cloned up to the 64-clone cap and every clone holds the whole set. About 3,600 variables hold more than 2,000 objects each.
  - Stripe hits the same budget the same way (10.7M entries plus 5.3M copies).
  - This is allocation and receiver merging. Separating it needs per-allocation or per-receiver contexts; within the existing 64-per-function limits they cannot separate thousands of schemas built through one `rebuild` call site, so contexts alone, under today's caps, would not bring OpenAI under the budget. The decision is Tim's: what context model (and what limits) the solver may use for schema-scale programs.

- **Performance.** On the OpenAI acceptance program the build takes about 6 s with the pass and 247 ms without. That is far over the 1.5× target. Possible fixes: caching `effect`'s constraint graph across builds, SCC collapsing, and tracking only values that can reach a key.
- **Order sensitivity.** The same input gives the same solve: modules and exports are walked in a canonical order (implementation.md, Data flow step 2). The solve is not order-independent, though. Clones and builtin rule invocations go to the first call sites to arrive, so an unrelated change that reorders execution can change precision and the budget verdict. Walking `effect_internal_analysed` in reverse execution order gives about 340k variables and goes over the budget; execution order gives 310k and stays within it. Making the caps independent of arrival order (choosing clone sites by rank, not by arrival) would remove this. It is open whether that is worth its cost.
- **Later increments.** Prefix narrowing of keys built from a constant prefix plus a run-time suffix (the `dynamic_key_prefix` fixture is red until then), and pruning class-instance services' prototype methods.
